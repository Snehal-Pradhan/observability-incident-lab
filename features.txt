# PulseOps: Features and Needs

## Part 1: Feature list

### Application
- Orders API with realistic dependencies (Postgres and Redis)
- Cache-aside reads: Redis first, Postgres on a miss
- Liveness (`/health`) and readiness (`/ready`) endpoints
- A deliberately flawed endpoint (`/customers/{id}/orders`) for the incident
- Fault injection toggle (latency, errors, pool limits), off by default
- Seed script for repeatable sample data

### Observability
- **Metrics:** per-route request rate, error rate, and latency histograms, plus runtime, DB pool, cache, and container stats
- **Logs:** structured JSON with `trace_id` and `span_id`
- **Traces:** spans across the HTTP handler, Postgres, and Redis
- **Exemplars:** click a latency spike and land on the exact trace
- **Cross-signal navigation:** metric to trace to logs, and log back to trace
- **Auto-provisioned Grafana:** datasources and dashboards load with no manual setup

### Reliability engineering
- Availability and latency SLOs with error budget math
- Multi-window burn-rate alerts (fast burn pages, slow burn tickets)
- Latency and DB pool saturation alerts
- A runbook for every alert
- Unit-tested alert rules (`promtool test rules`)
- Alert routing to Slack or email through Alertmanager

### Load and performance testing
- k6 scenarios: baseline, ramp-up, spike, soak, recovery
- Thresholds that fail a run when SLIs are breached
- One `make` command per scenario, with fixed parameters
- Before/after comparison on identical workloads

### Incident workflow
- One-command fault trigger (`make incident-1`) and fix (`make fix-1`)
- A full postmortem: timeline, root cause, evidence, fix, and verification
- Root cause found from telemetry, ending in `EXPLAIN ANALYZE`

### Engineering quality
- One-command startup (`make up`)
- Pinned image versions and a `.env.example`
- GitHub Actions CI covering rule checks, dashboard validation, compose validation, and a k6 smoke test
- Retention limits and low-cardinality labels
- ADRs documenting design decisions

### Presentation
- Architecture diagram (Eraser)
- Dashboard screenshots from a real run
- Investigation GIF and a demo video of 90 seconds or less
- Honest limitations, roadmap, and "What I learned" section

## Part 2: Needs

### Skills
| Area | Level needed |
|---|---|
| Go or Python (HTTP service, SQL) | Intermediate |
| Docker and Docker Compose | Intermediate |
| PromQL and Prometheus alert rules | Beginner to intermediate, you'll learn it by building |
| Grafana dashboards | Beginner to intermediate |
| OpenTelemetry instrumentation | Beginner, the docs are good |
| k6 scripting (JavaScript) | Beginner |
| SQL and Postgres query plans | Basic |
| Git, GitHub Actions, Makefiles | Basic |

### Hardware
- 8 GB RAM minimum, 16 GB is more comfortable (about 13 containers plus k6 at the same time)
- 4+ CPU cores
- About 10 GB free disk
- Note: load tests on the same machine compete with the stack for resources, so record your hardware in the results

### Software
- Docker 24+ and Compose v2
- Git and `make`
- k6
- `promtool` (comes with Prometheus, or run it through Docker)
- A code editor
- Screen recorder for the demo (OBS, or a built-in tool)
- GIF tool (ScreenToGif, LICEcap, or Kap)

### Accounts
- GitHub (repo and Actions)
- Slack workspace with an incoming webhook, or an SMTP email account, for alert delivery
- Eraser.io (free tier is fine) for the diagram

### Time (realistic estimate)
| Phase | Effort |
|---|---|
| Service and Docker setup | 1 weekend |
| Metrics and dashboard | 1 weekend |
| Logs, traces, correlation | 1 to 2 weekends |
| k6 load tests | 2 to 3 evenings |
| SLOs, alerts, runbooks | 1 weekend |
| Incident run and measurement | 1 weekend |
| Polish, video, README | 1 weekend |

Roughly 5 to 8 weekends of part-time work. Phase 3 (logs, traces, and exemplars) is usually where people get stuck, so leave buffer there.

### Things you must not skip
1. **Real measurements.** Every number in the README must come from your own runs.
2. **Diagnosing blind.** Have the fault enabled by a script and investigate from the dashboards, rather than from memory.
3. **Recording as you go.** Capture screenshots and notes during the incident, because recreating them later is painful.
4. **Finishing small.** Get one clean end-to-end flow before adding anything extra.

### Biggest risks
| Risk | Mitigation |
|---|---|
| Stack too heavy for your laptop | Lower retention, trim exporters, run k6 with fewer virtual users |
| Exemplars or trace-to-log links don't work | Budget extra time and check the Grafana datasource configuration first |
| Results vary between runs | Fix parameters, restart containers, and run each test 3 times |
| Scope creep (Kubernetes, extra services) | Keep them in the roadmap until v1 is done |
